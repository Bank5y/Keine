# DeepSeek 思考模式跨轮是否必须回传推理内容

调研问题见 [#114](https://github.com/Bank5y/Keine/issues/114)。只记事实，不给 Keine 的建议。

调研日期 2026-11-20。模型 `deepseek-flash`（定价页标注版本 DeepSeek-V4.1-Flash-1017），对照少量 `deepseek-v4-pro`（DeepSeek-V4-Pro-0813）。接口是 OpenAI 格式的 `POST https://api.deepseek.com/chat/completions`，非流式，请求体带 `"thinking": {"type": "enabled"}`，不设 `reasoning_effort`（默认 high）。

标记约定：**[未核实]** 表示没在一手来源里确认，也没有实测到。

## 结论速览

| 历史里带工具调用的助手轮次怎么回传 | 一次运行之内（还没有新的用户消息） | 跨轮（新一次运行，已追加新的用户问题） |
| --- | --- | --- |
| 原样保留 `reasoning_content` | 200 | 200，推理内容拼进上下文（`prompt_tokens` 增加，模型能复述其中内容） |
| 删掉 `reasoning_content` 字段，或设为 `null` | 200：服务端按 `tool_call_id` 自动补回原推理内容（`prompt_tokens` 与原样保留相同）；`tool_call_id` 不是服务端生成的就 **400** | 200，**不会**补回，推理内容不进上下文 |
| 设为空字符串 `""` | 200，推理内容不进上下文 | 200，推理内容不进上下文 |
| 只留最终回复（丢掉工具调用轮次和工具结果） | 不适用 | 200 |

- 跨轮 3 种做法 × 5 次样本，共 35 次第二次运行，**没有一次 400**，答案都正确并引用了课程原文。差别只在：丢掉工具结果后，模型每次都要重新调用 1–2 次工具才能作答；保留工具结果时 0–2 次。
- 推理内容很少：第一次运行（2–3 个工具步 + 最终回答）合计 22–216 个推理 token（73–408 字符）；工具调用步里经常是 0。同一次运行的输入是 3k–8k token。
- 官方文档写的是「all subsequent requests」都必须回传、否则 400，跨轮实测与此不符。实际触发 400 的只有：当前运行里（最后一条用户消息之后）有工具调用的助手消息缺推理内容，且服务端认不出它的 `tool_call_id`。

## 1. 官方文档原文

来源：[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)（中文版 [思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode)）。

开头的总则，按请求带不带 `tools` 区分：

> In subsequent requests, whether `reasoning_content` should be passed back and whether it will be concatenated into the context depends on whether the request carries the `tools` parameter:
> - If the request carries the `tools` parameter: the `reasoning_content` of all previous turns should be passed back to the API and will be concatenated into the context. See Tool Calls for details.
> - If the request does not carry the `tools` parameter: `reasoning_content` does not need to be passed back; even if passed to the API, it will be ignored and will not be concatenated into the context.

中文版：「若请求携带 tools 参数：历史轮次的 reasoning_content 均应回传给 API，并会被拼接进上下文。」「若请求未携带 tools 参数：reasoning_content 无需回传；即使传入 API，也会被忽略，不会拼接进上下文。」

「Tool Calls」一节（锚点 `#tool-calls`）：

> Please note that for requests carrying the `tools` parameter, the `reasoning_content` must be fully passed back to the API in all subsequent requests — even for turns where the model did not perform a tool call. If your code does not correctly pass back `reasoning_content`, the API will return a 400 error.

中文版：「请注意，携带了 tools 参数的请求，在后续所有请求中，必须完整回传 reasoning_content 给 API——即使该轮模型未实际进行工具调用。若您的代码中未正确回传 reasoning_content，API 会返回 400 报错。」

样例代码在 Turn 2（新的用户问题）里沿用 Turn 1 的完整消息，并说明：

> Additionally, in the Turn 2 request, we still pass the `reasoning_content` generated in Turn 1 to the API.

其他相关事实：

- 开关：OpenAI 格式 `{"thinking": {"type": "enabled/disabled"}}`；「Thinking mode is enabled by default, with the default effort being `high`」。来源同上。
- 模型名：[Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing) 只列 `deepseek-flash` 和 `deepseek-v4-pro`；Flash「Supports both non-thinking and thinking (default) modes」。`deepseek-flash` 就是字面的模型 id。
- [Create Chat Completion](https://api-docs.deepseek.com/api/create-chat-completion) 的请求参数里，assistant 消息的 `reasoning_content` 被写成「(Beta) Used for the thinking mode in the Chat Prefix Completion feature as the input for the CoT in the last assistant message」，没有提工具调用场景下的回传要求，与 Thinking Mode 页的说法不一致。响应的 `usage.completion_tokens_details.reasoning_tokens` 是「Tokens generated by the model for reasoning」。
- 文档没有提到服务端会按 `tool_call_id` 补回推理内容（见 3.2），这是实测推断 **[未核实]**。

## 2. 实验设置

一次性脚本放在会话临时目录，没有提交。请求格式沿用 `origin/prototype/first-turn-analysis` 的 `scripts/prototype-analysis/run.py`：系统提示词说明是探索助手、要求以课程原文为依据；课程是该原型用过的 5 篇中文维基条目组成的小课程（本地 `.scratch/analysis-proto/wiki/`）；工具只声明 `read_lesson` / `list_sections` / `search_course` 三个课程工具，在本地执行（没有接联网搜索，避免搜索结果的随机性）。

- **第一次运行**：用户问「Raft 的任期是什么，并对比 Paxos 里起类似作用的概念」，要求先查课程。模型每次都调用 2–3 步工具（`list_sections`、`search_course`、`read_lesson`），然后给出最终回答。
- **第二次运行**：在第一次运行的历史后追加新问题「Paxos 里 acceptor 收到编号比它已回应过的 prepare 更小的提案时怎么处理，引用原文」，照常跑工具循环直到作答。答案在第 04 讲「决议的提出与批准」：「承诺不再回复小于n的提案」。
- 第二次运行对历史做 7 种处理：
  - b：原样保留；
  - a1：所有助手消息删掉 `reasoning_content` 字段；
  - a2：所有助手消息的 `reasoning_content` 设为 `""`；
  - a3：只删工具调用步的；
  - a4：只删最终回复那一步的；
  - c1：只留最终回复，不带推理内容；
  - c2：只留最终回复，带它的推理内容。
- 同一历史下顺带测：不带 `tools` 参数、历史删掉推理内容；以及一次运行之内删推理内容（每个工具调用步追加到历史时就不带 `reasoning_content`）。
- 第一次运行重复 5 次，每次的历史分别跑上面所有处理方式。另外用手写的历史做了几组补充探测（3.2、3.3）。

## 3. 结果

### 3.1 跨轮：三种做法都不报错

5 次样本，每格是 5 次的取值。「工具步数」是第二次运行里调用工具的步数，「输入 token」是第二次运行各步 `prompt_tokens` 之和。

| 处理 | HTTP | 第二次运行工具步数 | 输入 token | 推理 token | 答案正确且引用原文 |
| --- | --- | --- | --- | --- | --- |
| b 原样保留 | 全 200 | 1, 1, 0, 1, 2 | 4.6k–7.9k | 14–455 | 5/5 |
| a1 全删字段 | 全 200 | 1, 2, 0, 1, 2 | 4.4k–10.3k | 54–289 | 5/5 |
| a2 全设 `""` | 全 200 | 1, 3, 0, 1, 2 | 4.6k–11.2k | 99–666 | 5/5 |
| a3 只删工具调用步 | 全 200 | 1, 1, 0, 1, 2 | 4.6k–8.0k | 136–420 | 5/5 |
| a4 只删最终回复 | 全 200 | 0, 1, 0, 1, 2 | 2.4k–8.0k | 119–535 | 5/5 |
| c1 只留最终回复 | 全 200 | 2, 2, 2, 1, 1 | 4.1k–7.6k | 57–252 | 5/5 |
| c2 只留最终回复 + 推理 | 全 200 | 2, 2, 2, 2, 2 | 3.9k–4.9k | 54–257 | 5/5 |

- 35 次第二次运行没有 400。耗时都在 4–10 s。
- 答案质量没有看出差别：35 份都答对「不回复」，并引用「承诺不再回复小于n的提案」或「不会再接受编号小于n的提案」。样本小，题目也只依赖工具结果、不依赖推理内容，不能排除更长、更依赖前文推理的对话会有差别。
- 只留最终回复时，模型每次都重新查课程（1–2 步）；保留工具结果时，第一次运行已经读过相关小节的样本可以 0 步直接作答。
- 缓存命中数（`prompt_cache_hit_tokens`）各处理之间波动很大，同一处理内也不稳定，看不出删推理内容对缓存的确定影响。

单独又用真实的工具循环历史做了两组对照（第一组工具步推理 0/49/75 字符，第二组 6 个工具步共 573 字符），追加「再用一句话总结一下」：

| 工具调用步 / 最终回复 | 第一组 `prompt_tokens` | 第二组 `prompt_tokens` |
| --- | --- | --- |
| 保留 / 保留 | 2190 | 2673 |
| 删字段 / 保留 | 2164 | 2498 |
| 设 `""` / 保留 | 2164 | 2498 |
| 删字段 / 删字段 | 2164 | 2498 |

全部 200。跨轮删字段和设 `""` 的输入 token 相同，都比保留少，说明跨轮时服务端不补回推理内容，就是直接不放进上下文。

### 3.2 一次运行之内：服务端按 `tool_call_id` 补回，认不出才 400

第一次在主实验里「一次运行之内删推理内容」，5 次全部 200，跑到最终回答。再拆开测（第一步真实调用拿到 `tool_calls`，第二步请求改写这条助手消息）：

| 第一步助手消息怎么回传 | 3 次结果 | 第二步 `prompt_tokens`（3 次） |
| --- | --- | --- |
| 原样保留 | 200 | 1042 / 1048 / 1057 |
| 删 `reasoning_content` 字段 | 200 | 1042 / 1048 / 1057（与保留相同） |
| 设为 `""` | 200 | 1042 / 1039 / 1043（第一步推理非空时变少） |
| 删字段，并把 `tool_call_id` 换成自造的 | **400** | — |

手写的历史（`tool_call_id` 为 `call_0`，不是服务端生成的）里，当前运行的工具调用消息不带 `reasoning_content` 或设为 `null`，`deepseek-flash` 和 `deepseek-v4-pro` 都返回 400：

```
{"error":{"message":"The `reasoning_content` in the thinking mode must be passed back to the API. (request_id: …)","type":"invalid_request_error","param":null,"code":…}}
```

同样的手写历史，后面追加一条新的用户消息之后再发，就是 200。content 为 `""`、`null` 或有文字都一样。

由此推断 **[未核实，文档没写]**：服务端只检查最后一条用户消息之后、带工具调用的助手消息；缺字段时用 `tool_call_id` 去找自己生成过的推理内容补上，找不到才 400；`""` 被当作「已回传」，不补。

### 3.3 回传的推理内容确实被模型读到

在手写历史的推理内容里埋一句「本次对话的暗号是 蓝鲸-7342」，跨轮问模型「之前思考里记下的暗号是什么，看不到就说看不到」：

| 暗号放在哪 | 请求带 `tools` | 结果 | `prompt_tokens` |
| --- | --- | --- | --- |
| 工具调用步的推理内容 | 是 | 3/3 说出「蓝鲸-7342」 | 855 |
| 最终回复的推理内容 | 是 | 1/3 说出，2/3 答「看不到」 | 855 |
| 工具调用步的推理内容 | 否 | 3/3「看不到」 | 416 |
| 不放暗号（对照） | 是 | 2/2「看不到」 | 834 |

带 `tools` 时两处推理内容都计入输入 token（855 比对照多 21），模型能读到；不带 `tools` 时被丢弃，与文档一致。`deepseek-v4-pro` 在工具调用步埋暗号时答「抱歉，这个我不能透露」，看起来也读到了（只测 1 次）。

### 3.4 顺带发现：不带 `tools` 但历史里有工具调用

历史里有工具调用、第二次运行的请求不带 `tools`（推理内容已删）：200，但模型把工具调用以原始标记写进了 `content`：

```
我先在课程原文里核对一些细节。

<｜｜DSML｜｜ calls>
<｜｜DSML｜｜ invoke name="search_course">
<｜｜DSML｜｜ parameter name="keyword" string="true">承诺</｜｜DSML｜｜ parameter>
…
```

只测了 1 次。

### 3.5 推理内容的体量

`usage.completion_tokens_details.reasoning_tokens`，字符数是 `reasoning_content` 的长度：

- 第一次运行（含工具调用，5 次）：每步 0–202 token；工具调用步多为 0–40 token（0–86 字符），第一步 5/5 是 0；整次运行合计 22–216 token（73–408 字符）。同一次运行的输入 3.2k–8.1k token，输出 605–707 token。
- 第二次运行（35 次）：整次运行合计 14–666 token（43–2220 字符）。
- 对照：只回传工具调用步的推理内容，每次运行在下一次请求里多出约 20–180 个输入 token（见 3.1 的对照表：26、175）。

## 4. 没覆盖到的

- 只测了非流式。流式与非流式的回传格式相同，未单独测 **[未核实]**。
- 服务端按 `tool_call_id` 补回推理内容能保留多久、是否绑定 API key，没有测；隔开较长时间再续同一次运行会不会变成 400 **[未核实]**。
- 没测 `reasoning_effort: max`、Anthropic 格式接口和 Responses API。
- 质量对比只有 5 组、一道题，题目依赖工具结果而不依赖前文推理。
- 文档的说法将来可能被服务端严格执行；本文记录的是 2026-11-20 的实际行为。
